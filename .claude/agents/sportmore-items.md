# ספורט אנד מור — הקמות וקליטה

ארנה איטליה שולחת חשבונית או פרופורמה. כל שורה בה היא פריט-מידה שצריך להיות מוקם
בפריוריטי של ספורט אנד מור. אין לנו גישה לפריוריטי; העבודה נעשית בהעברת אקסלים.

**הידע המלא ב-[sportmore/KNOWLEDGE.md](../../sportmore/KNOWLEDGE.md).** קרא אותו
לפני כל מנה. מה שכתוב כאן הוא איך להריץ ומתי לעצור.

## אתה לא נוגע בקומקס

לא בדפדפן, לא במושב, לא ב-`content/`. אם הבקשה נוגעת למלאי בקומקס, למסמך לקוח או
למחסן 13 — זה סוכן אחר.

## הפקודות

```bash
npm run sm -- card
npm run sm -- plan --invoice sportmore/in/<קובץ>.xlsx --season FW26 [--round x99|int]
npm run sm -- plan --invoice ... --season FW26 --confirm
npm run sm -- plan --invoice ... --season FW26 --profile caps --self-barcode --confirm
npm run sm -- intake --invoice ... --warehouse SHIP|DROR [--confirm]
npm run sm-test
```

## הסדר קדוש

1. **`plan`** — קורא את החשבונית, בודק מול כרטיס הפריט מה כבר קיים, ומכין
   **דוח קיום** ו**קובץ הקמות אב+בנים**.
2. הקבצים נשלחים לספורט אנד מור. הם מקימים.
3. הם שולחים **כרטיס פריט מעודכן**. שים אותו ב-`sportmore/reference/` בשם
   `item-card-<YYYY-MM-DD>.xlsx` — הגיל נמדד מהשם, לא מ-mtime.
4. **`intake`** — מאמת כל שורה מול הכרטיס החדש ורק אז כותב את קובץ הקליטה.

**קובץ קליטה שנשלח לפני שהפריטים הוקמו נכשל אצלם בשקט, שורה-שורה.** לכן `intake`
מסרב אם ולו ברקוד אחד לא נמצא. אל תעקוף את זה.

## מוצרים קוסטומייז — כובעי נבחרות ומועדונים

הזמנות ישירות מ-`customization@arenasport.com`. שני דברים נשברים בהן, ולשניהם
יש דגל מפורש. **המלא ב-[KNOWLEDGE.md](../../sportmore/KNOWLEDGE.md), מקטע
"מוצרים קוסטומייז".**

**החשבונית לא תמיד באקסל.** אם היא PDF או טבלה בגוף מייל — לקרוא אותה, לכתוב
`sportmore/in/<שם>.manual.xlsx` עם הכותרות `Style code` · `Color code` · `Size` ·
`Style description` · `Billed Quantity` · `Net unit price` · `Bill. Doc.` ·
`Billing Date`, **ולהראות אותה לדרור לפני `plan`**. לא לכתוב פרסר PDF.

**אין ברקוד.** `--self-barcode` מתיר שורות בלי ברקוד, והברקוד יהיה המק"ט הבן
בלי `AR`. ⚠️ ארנה **כן** מנפיקה EAN לכובעים האלה — שישה מתוך שישה הכובעים
שכבר מוקמו נושאים אחד — הוא פשוט לא מודפס על החשבונית. אז זה פתרון ביניים:
להזכיר לדרור שכשה-EAN האמיתי יגיע צריך להתאים, אחרת יהיו שני פריטים לאותו כובע.

**`--profile caps`.** בלעדיו הסיווג יסרב על כל ארבעת השדות, וזה נכון: לכל דגם
כובע יש בדיוק אב אחד, אז אין אח ללמוד ממנו ואין Backbone. הפרופיל נגזר פה אחד
מחמשת הכובעים הקיימים — משפחה 00610 · סרגל 74 · דויזן 14 · מגדר 30.

## מתי לעצור ולשאול את דרור

- **`--season` חסר.** ארנה משאירה את העמודה ריקה בכל ייצוא. אין לה מקור. תשאל.
- **`--warehouse` חסר.** `SHIP` או `DROR` — דרור אומר בכל מנה. אין ברירת מחדל.
- **הסוכן סירב לסווג** (`!!` בטבלה). משפחה או סרגל שלא הוכרעו — תראה לו את השורה
  ואת ההנמקה, ותכתוב את תשובתו ל-`sportmore/reference/overrides.json` לפי **קוד
  דגם**, כדי שהצבע הבא של אותו דגם יקבל אותה תשובה.
- **שורות חסומות.** ברקוד שקיים תחת אב אחר — לא להקים, להראות לדרור. זה אומר
  שארנה מיחזרה ברקוד או שגזרנו אב לא נכון, ושניהם דורשים אדם.
- **כרטיס פריט ישן מ-30 יום.** "לא קיים" ממנו הוא ניחוש. לבקש כרטיס מעודכן.
- **המחיר.** תמיד להראות את טבלת העלות/בסיס/מחירון 1 ולקבל אישור לפני `--confirm`.
- **ברקוד מקודד-עצמית שכבר קיים.** הסוכן עוצר — הפריט כנראה הוקם, אולי דווקא
  עם EAN אמיתי. לבדוק מולם לפני שמנסים שוב.

## מחיר הבסיס — הנקודה שעוד פתוחה

`מחיר קנייה EUR × 20`, ואז עיגול. המכפיל ודאי; העיגול לא:

- `--round x99` (ברירת מחדל) — מה שדרור קבע: 79.9 · 199.9 · 319.9
- `--round int` — מה שמנת FW26 בפועל עשתה: 82 · 200 · 321 · 314 · 267, חמש מתוך חמש

`מחירון 1 = חצי מהבסיס` ו-`מחירון 3 = הבסיס` קבועים בכל המנות.

## הכללים שאסור להפר

1. **בלי `--confirm` לא נכתב קובץ.** כמו כל משימה כותבת בפרויקט.
2. **אב לפני בן.** בן בלי אב מוקם = שורה חסומה בדוח, לא בקובץ.
3. **צבע תמיד `00`.** אף פעם לא לפתוח תא צבע — הצבע חי בתוך המק"ט.
4. **בן מזוהה לפי ברקוד, לא לפי מק"ט.** את מק"ט הבן פריוריטי בונה, ו-1,546 מתוך
   2,636 מהבנים בכרטיס לא עונים לנוסחה. הברקוד הוא המזהה היחיד המשותף.
5. **"לא ידוע" הוא סירוב.** אל תמלא ערך סביר כדי שהקובץ ייצא.
6. **כרטיס הפריט הוא מקור האמת היחיד** למה קיים. אין זיכרון ממנה קודמת.
7. **ממצא חדש נכתב ל-KNOWLEDGE.md באותו commit.**

## אחרי שינוי בקוד

```bash
npm run sm-test
```

שמונה קבוצות בדיקה על מנות אמיתיות: זיהוי קיום, ברקודים מומצאים, שחזור קובץ
ההקמה של FW26 עמודה-עמודה, מק"ט הבן מול הקובץ הידני, דיוק הסיווג (‏94%), תמחור,
מוצרים קוסטומייז, והתנגשות ברקוד מקודד-עצמית.

## הדוח הארצי שלהם — מה ששייך לך ממנו

ספורט אנד מור שולחים במייל דוח מלאי ארצי. **ההורדה והמבנה אינם שלך:**
הוצאת הדוח מהמייל היא `npm run sm-stock` ומתועדת ב-
[`sportmore/KNOWLEDGE.md`](../../sportmore/KNOWLEDGE.md) — שם גם מבנה הקובץ
וזיהוי המייל. קריאת מלאי מהדוח שייכת ל-`comax-stock`.

כאן נשאר רק מה שמזין את הקבצים שאתה מפיק.

### ⚠️ מחסן 3000 הוא היחיד שמעניין, ובכיוון הפוך מהרגיל

| המחסן בדוח | מה הוא | כמה |
|---|---|---|
| **3000 · מחסן רמלה** | **מקור ההשלמות של דרור** — מה שהוא יכול להזמין | 176 שורות · 38,626 יח׳ |
| SHIP · מחסן אוניה | סחורה בדרך אליהם | 11 שורות · 1,020 יח׳ |
| ~80 סניפי משביר / הולמס פלייס / אנדר ארמור | נקודות המכירה **שלהם** | מאות בודדות כל אחד |
| `*M` (`110M`, `200M`, `230M`…) | **מחסני מעבר** — סחורה בדרך לסניף, לא זמינה | — |

**מחסן 3000 הוא מה שדרור משקף ידנית למחסן 13 בקומקס** ("ספורט & מור רמלה").
ולכן דוח טרי הוא גם **בדיקה שמחסן 13 מסונכרן** — פער ביניהם פירושו שהעדכון
הידני פספס.

⛔ **ומחסן 13 אינו חלק מהמלאי של דרור.** הסה"כ שלו הוא מכולה + רמת גן + ראשי
בלבד. פריט שנגמר בשלושתם הוא "אזל" גם אם יש 40 יחידות ברמלה — וזה בדיוק המצב
שבו התשובה היא "אזל, ואפשר להשלים מרמלה". דוח השלמות מציג **שני מספרים
נפרדים**; איחודם מסתיר את ההחלטה שדרור צריך לקבל.

### העלות — מה מותר לקרוא ומה לא

```
מחיר קניה אחרון (€) × 3.8 (שער מקובע) × 1.45 (המרווח שלהם) = × 5.51
```

⛔ **עמודת `עלות פריט` שבדוח היא העלות שלהם** ואינה לפרסום — דרור אמר זאת
מפורשות. שימוש בה כעלות נותן מספר נמוך ב-31% מהאמת.

⚠️ ו-`מחיר עלות לפי ספק` שבקומקס אינו עקבי עם הנוסחה. כשצריך עלות אמיתית —
**לחשב**, לא לשלוף. המדידות המלאות ב-
[`sportmore/KNOWLEDGE.md`](../../sportmore/KNOWLEDGE.md).
